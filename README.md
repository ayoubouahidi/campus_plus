# Campus Plus API

This project is a Django API for campus departments, clubs, members, and
club events.

## Data modeling

### Department

A department has a title. One department can have many clubs, members, and
events.

### Club

A club belongs to one department. It has:

- name and description
- a club head or president
- contact email
- meeting day, time, and location
- active status
- created and updated dates

A club name must be unique inside its department. A club can have many members
and many events.

### UserMember

`UserMember` is the campus profile for a Django user. It has:

- generated username
- first name and last name
- email from the Django user account
- year of study
- department and club
- role and event date
- profile image

A member can have one Django user account. The Django user stores the password
and is used for login.

### ClubEvent

An event belongs to a department and can belong to a club. It has:

- name and description
- start and end date
- location
- status
- event image
- created and updated dates

The event status can be `planned`, `ongoing`, `completed`, or `cancelled`.

Images must be a real JPEG, PNG, or WEBP file and must be smaller than 2 MB.

## Filtering and search

Club events can be filtered by department:

```text
GET /api/club-events/?department=1
```

They can also be filtered by a word in the event name or description:

```text
GET /api/club-events/?category=football
```

Both filters can be used at the same time:

```text
GET /api/club-events/?department=1&category=football
```

The event endpoint also supports search. Search checks the event name,
description, and department title:

```text
GET /api/club-events/?search=technology
```

Departments can be searched by title:

```text
GET /api/departments/?search=computer
```

## Main API endpoints

```text
POST /api/signup/
GET  /api/departments/
GET  /api/clubs/
GET  /api/club-events/
GET  /api/members/
```

Signup needs first name, last name, email, department, year of study, and
password. The username is generated by the server and a token is returned.

Only an admin can create, update, or delete members and clubs. An admin or the
head of a club can create events for that club.

## Accounts and dashboard APIs

`accounts.User` is the authentication identity (`AUTH_USER_MODEL`) and extends
Django's `AbstractUser`. Its primary key is a `BigAutoField`; the table is
`accounts_user`, `username` remains the login field, and Django's inherited
`UserManager` provides `create_user`/`create_superuser`. `USERNAME_FIELD` is
`username` and inherited `REQUIRED_FIELDS` is empty. `first_name` and
`last_name` are inherited 150-character fields; `email` is the inherited
254-character `EmailField`. Additional fields are `forty_two_id`
(`PositiveIntegerField`, unique, nullable), `role` (`CharField`, max 20,
default `STUDENT`), `campus` (`CharField`, max 100), and `avatar_url`
(`URLField`). Roles are `STUDENT`, `BOARD_MEMBER`, and `SUPERADMIN`.

`core_data.UserMember` remains the club/department profile and links one-to-one
to that identity. The team has agreed that `phone` belongs on `UserMember`;
the current branch still has a temporary `User.phone` field and must be aligned
with Ahmed's model change before the migration contract is final. Board
authorization uses `accounts.ClubBoardAssignment`, not ordinary `UserMember`
club membership. Each board user has one explicit club assignment; a club may
have multiple board users. `Club.head` remains an explicit head relationship.

`accounts.0001_initial` depends on Django auth migration `0012`; the initial
dashboard migration depends on `core_data.0006` and the swappable user model.
The test suite migrates a fresh temporary database successfully. No
existing-data user transition or rollback rehearsal has been completed.

The internal `POST /auth/sync` endpoint requires `x-internal-key` to match
`BACKEND_INTERNAL_KEY`; it must only be reachable from the Next.js container.
Configure `SUPERADMIN_LOGINS` as a comma-separated list and optionally
`ALLOWED_42_CAMPUSES` as a comma-separated allow-list. Do not commit `.env`
files or send their secret values through chat.

The request uses the camelCase fields sent by the dashboard's current
`auth.ts`: `fortyTwoId`, `login`, `email`, `firstName`, `lastName`, `imageUrl`,
and `campus`. The response is `{ "token": "<DRF token>", "user": { ... } }`;
`user.id` is a JSON integer. The dashboard's current `BackendUser` declaration
types `id` as a string and its session callback only accepts strings, so the
frontend must normalize the ID with `String(data.user.id)` (or adopt a numeric
ID type) before the login contract is considered integrated.

Authenticated user endpoints:

```text
POST      /api/auth/login/        # JSON: {"email": "...", "password": "..."}
GET/PATCH /api/me/             # PATCH only accepts phone
POST      /api/auth/logout/    # deletes the current DRF token
```

Email/password login returns `{ "token": "<DRF token>", "user": { ... } }`,
matching `/auth/sync`. Login requires exactly one case-insensitive email match;
Ahmed should make `/api/signup/` reject duplicate email addresses so new
registrations satisfy that contract. `/api/signup/` already accepts
`first_name`, `last_name`, `email`, `year_of_study`, `department_id`, and
`password`, with optional `club_id`; it returns `{ "token": "...", "member":
{ ... } }`.

The club-board endpoints are under `/api/board/`; membership requests and
announcements are always scoped to the current user's explicit
`ClubBoardAssignment` or `Club.head` relationship. A `UserMember.club_id`
membership alone never grants management access. Ahmed's event and RSVP APIs
remain the source of truth for event management and registration counts.

Superadmin endpoints require the `SUPERADMIN` role:

```text
GET   /api/superadmin/stats/
GET   /api/superadmin/organizations/
PATCH /api/superadmin/organizations/{id}/       # {"is_active": false}
GET   /api/superadmin/users/?search=...&role=...
PATCH /api/superadmin/users/{id}/               # {"role": "...", "club_id": 1}
GET   /api/superadmin/roles/distribution/
GET   /api/superadmin/events/weekly/
GET   /api/superadmin/audit-log/
```

User and audit-log lists are paginated. Assigning `BOARD_MEMBER` requires a
club; role and organization status changes are recorded in the audit log.

### Custom-user migration coordination

The project has historical `core_data` migrations created when Django's
default user model was configured. Fresh databases now migrate with
`accounts.User`, but switching `AUTH_USER_MODEL` does not automatically move
rows or rewrite foreign keys in an already-migrated database. Before applying
this branch to any database with existing data, coordinate a data-preserving
migration with Ahmed: copy auth users, remap `UserMember.user` (and every
other user foreign key), and verify the resulting foreign-key constraints.
Do not run migrations against a shared or production database until that plan
has been reviewed and backed up.

## Real-time calendar and JWT development

The ASGI application serves `/ws/calendar/`. An authenticated, active Django
user joins `calendar_updates` and receives `connection_established`, followed
by calendar event broadcasts. Redis is the configured channel layer: it lets
different Django processes deliver messages to connected clients.

`WS_AUTH_BACKEND` selects WebSocket authentication:

- `token_dev` (default): existing DRF query-token authentication, permitted only
  with `DEBUG=True`. Use test accounts locally; URLs can enter access logs.
- `jwt`: verifies a SimpleJWT access token from exactly one `ws_access` cookie.
  Invalid, expired, duplicate, malformed, refresh, inactive-user, and
  missing-user credentials are rejected. Query tokens do not authenticate in
  this mode. There is no fallback to development tokens.
- An unsupported value prevents application startup.

The API still uses DRF tokens. Signup at `/api/signup/` returns a DRF token;
it does **not** issue JWTs. The frontend session remains a mock. No JWT login,
cookie issuance, refresh, logout, or 42 OAuth integration exists in this
checkout. A NextAuth session token is not an established backend credential.

For local JWT mode, start the existing Daphne application with
`WS_AUTH_BACKEND=jwt .venv/bin/daphne backend.asgi:application` after configuring
the environment, database, and Redis. This does not create a login endpoint.
The authentication teammate must agree on issuance and set the `ws_access`
cookie with `HttpOnly`, `Secure`, an appropriate `SameSite` policy, and a path
covering `/ws/calendar/`. Middleware cannot infer these attributes from an
incoming Cookie header. Keep access and refresh credentials out of URLs.

No `SIMPLE_JWT` overrides are currently declared. Installed defaults use
HS256, Django's secret key, a five-minute access lifetime, `user_id` mapped to
the Django user's `id`, and `token_type=access`. Issuer and audience are not
configured; verification respects them when configured. These defaults are
an experimental verification contract, pending agreement with the login owner.

Origins are checked using `AllowedHostsOriginValidator` and `ALLOWED_HOSTS`.
This is a host-based policy, not an explicit HTTPS-origin allowlist. All
authenticated users currently share the calendar group; private notifications
are not implemented. Authentication runs at connection time: expiry, account
disablement, logout, and revocation do not yet close an existing socket.

### Environment and Docker

`backend/settings.py` loads `.env`; never commit it or print its contents.
Required settings include `DJANGO_SECRET_KEY` and `REDIS_URL`. SQLite is the
local default. Setting `POSTGRES_HOST` selects PostgreSQL and requires
`POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD`; `POSTGRES_PORT` defaults
to 5432. `DEBUG`, `DJANGO_ALLOWED_HOSTS`, and `WS_AUTH_BACKEND` control the
development and authentication settings.

Compose defines `web`, `frontend`, `nginx`, `redis`, and `db`. Inside its network,
the database is `db:5432` and Redis is `redis:6379`; these names are not local
host service addresses. Nginx exposes HTTP on 8080 and HTTPS/WSS on 8443 and
proxies `/ws/` to Daphne. <!-- # [ahmed] Docker JWT configuration. -->
Compose now sets `WS_AUTH_BACKEND: jwt` for `web`. Rebuild and recreate that
service with `docker compose up -d --build web` to apply the current code and
configuration. A running older image may still lack JWT support. Cookie
issuance is still required for browser authentication.
The HTTP redirect currently omits the mapped HTTPS port; local HTTPS clients
should connect to port 8443 directly.

Compose certificate generation is provided by
`infrastructure/nginx/gen-certs.sh`; inspect it before running. Docker startup,
TLS trust, and WSS have not been verified in this session. Avoid deleting
database volumes as a troubleshooting step.

### Verification

```bash
.venv/bin/python manage.py check
.venv/bin/python manage.py test realtime.test_jwt -v 1
.venv/bin/python manage.py test -v 1
```

WebSocket tests use an in-memory channel layer and temporary SQLite database;
they do not verify Redis, PostgreSQL, Nginx, or browser cookie issuance. In a
restricted sandbox, handshake timeouts can result from blocked local sockets;
the same JWT tests passed outside that sandbox. Check the traceback and runtime
restrictions before changing application logic.

Audited runtime: Python 3.14.10, Django 6.1.3, Channels 4.3.2, Daphne 4.2.3,
channels-redis 4.3.0, DRF 3.18.3, SimpleJWT 5.5.1, PyJWT 2.15.1. SimpleJWT's
installed metadata lists Django through 5.2 and Python through 3.13; support
for this newer runtime needs separate compatibility review. Docker installs
`requirements.txt`, which already declares SimpleJWT.
